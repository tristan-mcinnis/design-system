# Follow-up background soak — 15-minute read-only observation

Date: 2026-09-06 (CST). Owner: `docs/performance/20260906-followup/`.
Scope: a longer background CPU / physical-memory (footprint) soak of the running
house fleet, excluding real-use responsiveness (hotkey-to-panel, typing stalls,
recording latency). Read-only — no app edits, no commits, no restarts, no model
calls, no captures.

This is a follow-up to `PERFORMANCE.md`, whose first fleet sample was 31 samples
over 61.4 s. This run lengthens the observation window ~15× to look for slow
drift you cannot see in a minute.

---

## What was run, and how

Same read-only snapshot tool as the prior fleet sample, plus a separate START
footprint capture using the tool's own discovery logic (same matchers, same
argv anchoring) so the start PIDs match what the snapshot observes.

```
python3 bin/performance-snapshot \
  --duration 900 --interval 5 --footprint \
  --output-dir docs/performance/20260906-followup \
  --output followup-15min-observation \
  --git-repo ../memory-menubar --git-repo ../memory-recall --git-repo ../local-models
```

Plus a START capture immediately before the first sample:

```
python3 /tmp/start_footprint.py --out .../start-footprint.json   # /usr/bin/footprint --noCategories, no sudo
```

Read-only by contract: no root (euid 501), no process signals/restarts, no
network, no screenshots, no screen/private captures, no clipboard. The tool
matches full argv in memory only; the JSON carries safe labels (pid, ppid,
service, execution basename), never a raw command line.

### Window and monotonicity

- Samples: **181** over a monotonic clock. Elapsed strictly increases
  0 → **912.75 s** (15.2 min), no discontinuity, so the CPU-delta windows are
  valid. `wall_elapsed_seconds = 913.336`.
- Environment: Apple M5, 10 cores (4 performance / 6 efficiency), 32 GB,
  macOS 26.5.2 (build 25F84), kernel 25.5.0.
- **AC power:** `pmset -g batt` reports *Now drawing from 'AC Power'*,
  InternalBattery-0 **100%; charged**. Consequently battery-life, watts, and any
  "idle-controlled / energy-saving" claim are **not measured** here.

## Result in plain language

No sustained upward memory trend was evident in this 15-minute observation.
Endpoint footprints were unchanged except for Memory, which rose by 1 MiB. The single most active background
process is the screen-context collector (screenctx), and its resident memory
drops and climbs back to the same baseline rather than growing monotonically.
The only processes that moved are one-shot provider helpers that appear for a
moment and vanish — these are censored out of the steady-state read, not idle
CPU.

There was no sustained growth signal. Every menu-bar app stayed below the
0.5%-of-one-core target in this working-session observation. This does **not** certify long-term
energy or a multi-hour leak.

The three `usage` descendants are one-shot provider/API reads spawned by the

**Censoring rule applied:** a process is only counted in the steady-state CPU
and footprint read if it was observed for the full window (first_sample_index ==
0 and last_sample_index == 180). The 4 transient rows are reported separately.

## RSS trajectory — robust summary

RSS is a screening metric; footprint is the authoritative physical number. The
RSS trajectory is another screening signal, not necessarily the first place a
leak appears. It is mostly flat for steady processes except screenctx.

- **Flat (p10 ≈ median ≈ p90, all within a few MB):** cotype, dictation, dictation
  bridge, local-models-bar, local-models-daemon, local-models-daemon child, vision
  server, vision tracker, memory, quick-launch, rti, usage, pocket-tts. None shows
  monotonic growth; start ≈ end for each.
- **screenctx 98622** is the only variable one:
  - Sits at **~193 MB** for the first ~477 s (idx 0–90).
  - Dips to **~104–119 MB** during ~477–625 s (the cause was not instrumented).
  - Climbs back to **~127–187 MB** from ~639 s to the end, ending at **187.5 MB**,
    i.e. returning to the same ~190 MB baseline where it started.
  - CPU stays 0.2–1.8 % of a core throughout, no burst.
  - **Read:** memory returned near its starting level, with no sustained
    upward-only drift. This does not identify the cause or exclude a leak.
- **Robust reading:** report the median, not min/max, for screenctx (median
  192.6 MB, p10 115.8 MB, p90 193.5 MB). min/max alone would overstate a leak
  or an idle floor depending on which quiet/active phase you caught.

No steady process shows a monotonic RSS increase across the window, so there is
no 15-minute growth signal.

## Footprint before vs end

Physical footprint (the better memory screen) is essentially unchanged over the
window. The only delta is `memory` 10 → 11 MiB (+1 MiB); everything else is
identical.

- Steady sum of `phys_footprint`: 6366 → **6367 MiB** (+1 MiB). Additive shadow
  total — shared/model pages may be counted more than once; this is **not** a
  system-wide free-RAM claim.
- Per-process before/end are in the table above.

**RSS is not footprint**; this run makes that concrete:
- vision server 1175: RSS **28.2 MB**, footprint **2657 MB** (canonical vision
  model ~2.7 GB).
- dictation bridge 90734: RSS **62.0 MB**, footprint **1568 MB**.
- local-models-daemon child 54438: RSS **1036 MB**, footprint **511 MB** (shared
  model pages counted in RSS, not private footprint).

Do not read a leak from RSS, cache growth, or the sum of shared RSS. Footprint
is the reference; it is flat.

## What this shows, and what it does not

**Shows (in scope — longer background soak):**
- No 15-minute upward drift in footprint or RSS for any steady process.
- All menu-bar apps are far under the 0.5%-of-one-core idle budget:
  memory 0.010, quick-launch 0.016, usage 0.066, cotype 0.184, rti 0.267 (% of
  one core). screenctx (0.812 %) is a collector, not a menu-bar app.
- Only one local-models *vision* tree is present (pid 1175 + tracker 75565); the
  earlier duplicate wildcard-bound server (831 MB footprint) is gone, consistent
  with the shipped Local Models ownership fix.
- The only non-trivial CPU motion comes from intermittent provider reads (usage
  descendants), which is product behavior (hidden clipboard/provider monitoring),
  not idling.

**Does not show (hypothesis not measured — stated clearly, not implied):**
- **Battery life / watts / idle-controlled energy:** not measured. The host is on
  AC power at 100 % and charged; no wakeup or energy counters were read. No
  `powermetrics` — it needs privilege the read-only contract and this run did not
  request. Energy/wakeups remain unmeasured.
- **A leak test.** 15 minutes is materially longer than the prior 61 s baseline
  but it is still not an hours-scale leak test, and it is one session. Flat
  footprint and a non-monotonic screenctx RSS are suggestive of no growth, not a
  proof of a leak over a longer horizon. USE `footprint`, not RSS, for any leak
  follow-up.
- **Real-use responsiveness:** hotkey-to-panel, typing stalls, recording
  latency, provider-refresh feel — explicitly excluded per this task's scope.
  Those need UI instrumentation, not the process snapshot.
- **Controlled idle lab result.** This is a live observance of the running fleet;
  the parent noted other agents were reading/editing/running mock tests during
  the window, so this is not a quiet-lab idle certification. The flatness despite
  that makes the background picture more robust, not less.
